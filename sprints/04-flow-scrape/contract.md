## 2. 構文の妥当性の判定方法（PAD に貼り付けて確かめられないため）

Evaluator は PAD に貼り付けられないので、定義テキスト（Robin 構文）の正しさは次の **二重化** で判定する。テキストが PAD の版の違い等で貼り付けられなくても、人が手順書の表だけでフローを手作業で再現できることを合格の条件とする（4-3）。

1. **アクション表との1対1対応**：手順書に、定義テキストの全アクションを上から順に並べた「アクション表」を載せる。各行に `No`・`docs/flow.md` の手順番号（例：3-2）・PAD デザイナーの日本語表示のアクション名（例：「Web ページのコンテンツを待機」）・主な設定値（UI 要素／セレクター、入力値、タイムアウト、文字コード等）・生成される変数・エラー時の設定、を書く。定義テキストのアクション行（コメント・空行・`END` を除く）と表の行が、同じ順・同じ数で対応していること。
2. **机上の構文チェック**（定義テキストに対して Read・Grep で確認）：
   - 各アクション行が `モジュール.アクション` 形式（例：`WebAutomation.…`・`File.…`・`Variables.…`）、または `SET`・`IF`・`LOOP FOREACH`・`ON BLOCK ERROR`・`BLOCK`・`EXIT`・`#` コメント等の制御構文である
   - `IF`／`LOOP`／`BLOCK`／`ON BLOCK ERROR`／`SWITCH` 等の開始と `END` の数・入れ子が対応している
   - 文字列リテラルは `$'''…'''` 形式で閉じており、文字列中の変数参照は `%変数名%` で `%` が対になっている
   - 使用する変数はすべて、使用より前の行で生成（`SET` やアクションの出力 `=>`）されている、または手順書の変数表で「入力変数・PAD 上で設定」と明記されている
   - UI 要素を参照する場合（`appmask[...]` 等）は、その UI 要素が手順書の UI 要素表に同じ名前で載っている。定義テキストの先頭に UI 要素リポジトリの定義（`# [ControlRepository]` 等）を含める場合は、そこに書かれたセレクターが UI 要素表と一致している
3. 上記で判定できない PAD 固有の細部（アクション名の正確な綴り、列挙値の名前等）は人のレビュー②で確認し、本スプリントでは採点しない。
